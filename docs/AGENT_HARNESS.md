# Agent harness

How ExportMate's AI follows agent and harness engineering practice: what each control is, where it lives in `ai/server`, and what is not done yet. The principle: improve the system around the model rather than wait for a better model, and turn every failure into a rule, a check or a test (the "ratchet").

## The agents

| Agent | What it does | Pattern | Model | Can change data? | Human in the loop | Record |
| --- | --- | --- | --- | --- | --- | --- |
| Assistant (`agent.js`) | Answers questions about stock, news alerts, sources, the company profile and how to use ExportMate | Single Google ADK `LlmAgent` (Agent Development Kit for JS), ReAct loop (plan → call tools → observe, at most 6 steps) plus a deterministic auditor | Routed per question (`router.js`, `models.js`): `GEMINI_MODEL_SIMPLE` (default gemini-3.5-flash-lite) or `GEMINI_MODEL_COMPLEX` (default gemini-4-argon) | No: all six tools are read-only | Answers are informational. One that still fails the auditor after its revision is shown marked **Needs review** (`status: needs_review`) | `audits` document per answer |
| News scanner (`scan.js`) | Reads enabled feeds daily, asks which SKUs each new article affects, raises alerts | Batch pipeline with a structured-output (JSON schema) model call | `GEMINI_MODEL` (default gemini-3.5-flash) | Writes alerts, articles and the vector index only | Source changes are limited to company owners and editors (checked against the backend). Alerts are advisory | `scans` document per run |

Risk tier for both: low. Neither sends messages, spends money or deletes records. When actions arrive (drafting and sending supplier messages, backend phase 3), they follow `backend/docs/REQUIREMENTS.md` §4.7: drafted, approved by a person (who/when/hash of the exact text), then sent once with an idempotency key.

**Why one agent and not many.** `docs/agent-architecture.excalidraw` sketches a multi-agent pipeline (scouts, change detector, verifier, per-firm A1–A5). Today's tasks are small and sequential, so one tool-using agent with a separate deterministic auditor is cheaper, faster and easier to debug. Split into agents when a step becomes independent and parallel (per-jurisdiction scouts), or needs different permissions (the backend's order analysis).

## Layer by layer

| Layer | Control | Where |
| --- | --- | --- |
| **Policy (ratchet)** | The system prompt is built from `RULES`. Each rule says which failure it prevents (`prevents`), and `POLICY_VERSION` (a hash of the rules) is stored on every audit, scan and eval result, so behaviour changes can be traced to policy changes. The scan's rules are versioned the same way (`SCAN_POLICY_VERSION`). | `policy.js`, `scan.js` |
| **Context / RAG** | Firestore vector search (gemini-embedding-001, 768-d, cosine) with a document-type metadata pre-filter. A pool of 3× the requested results is reranked with BM25 over the candidates, so exact HS codes, SKUs and rule names (4412.33, PLY-103, EUDR) count (hybrid retrieval). Exact facts (counts, totals) come from `query_inventory`, never from search hits. | `rag.js`, `rerank.js` |
| **Freshness** | News results carry `ageDays`. The `dated-evidence` rule makes the assistant give the date and warn when news older than 30 days is used as the current rule. | `agent.js`, `policy.js` |
| **Tool harness** | The model never runs a tool directly. `toolGateway` looks the tool up in the registry, checks scope (a tool runs only when the turn has what its scope names: `company` tools in a signed-in company workspace, `orders` and `playbook` tools when the company backend or the browser demo supplies them, so they are neither offered nor allowed elsewhere; a company chat never uses what the client sends), validates arguments against the declared schema (types, enums, required, unknown keys), enforces a per-turn budget (16 calls, 8 per tool), runs with a timeout and retries only transient failures (timeouts, network errors, 429/502/503/504, gRPC UNAVAILABLE and similar), never 400/401/403/404. Each refusal comes back to the model as a fixable error and lands in the audit with an `errorKind`. Model calls retry transient errors the same way. | `gateway.js`, `agent.js` |
| **Orchestration** | Google ADK runs the loop: an `LlmAgent` (one per turn, so its prompt and tools belong to that company and its gateway) and a `Runner` over an in-memory session that holds the conversation the client sent. The harness hooks into ADK: each registry tool is an ADK tool that calls the gateway; ADK's model callbacks count steps (bounded at 6; the last step forbids tool calls) and record each plan, draft and answer; a plugin sends calls to tools the agent wasn't given through the gateway too, so they are refused and audited; a `Gemini` subclass retries transient model errors. The calls of one step run one after another (ADK's order). Recovery: transient retries, one auditor-driven revision (sent as a second message in the same ADK session), then `needs_review`. | `agent.js` |
| **Model routing** | Each question goes to a tier by rules, not a model call (free, instant, tested against every golden case): **simple** (small fast model, low thinking) for a single lookup, count, how-to or decline; **complex** (the bigger latest model, medium thinking; high made up to 13 tool calls per answer for the same results) for follow-ups, several SKUs, arithmetic or exposure, trade rules (duties, EUDR, tariffs), judgement (why, compare, should, risk), pasted third-party text, instructions aimed at the assistant and long questions. Vietnamese keywords count too. If the auditor sends a simple-tier draft back, the revision runs on the complex model (`route.escalated`). Every model call is given a thinking level, not a budget, because Gemini 4 rejects budgets. The tier, its reasons and the model of each step are on the audit. | `router.js`, `models.js`, `agent.js` |
| **Caching** | A question already answered isn't sent to Gemini again. The `answer_cache` collection (shared by every instance) maps a key to the audit that answered it. The key covers the normalised conversation, the company and the sources it switched off, the policy version, both tier models, the date and a fingerprint of everything the tools read (stock, sources as this company sees them, the latest finished scan, the company profile, the help guides). A scan, a source change, a stock edit or a profile edit makes a new key, so a stale answer is never served. Only clean answers are stored: status `ok`, every check passed, no tool error, no live tool (`query_orders` and `get_playbook` read Postgres or the demo's own data, outside the fingerprint; which of them were offered is in the fingerprint). A reused answer gets its own audit with a `cache` step naming the original, then the original's steps, citations and checks, and no model usage. Entries expire after two days (Firestore TTL on `expireAt`). Evals bypass the cache. Below that, tools cache stock, alerts and sources in memory for a minute, and query embeddings are kept per instance. The news scan never assesses an article twice: it skips any article an earlier scan analysed. | `answer-cache.js`, `agent.js`, `rag.js`, `scan.js`, `infra/terraform/ai_service.tf` |
| **Verification (auditor)** | Every draft is checked before it is accepted: citations resolve to retrieved evidence, every 3+ digit figure and every percentage appears as a whole number in the user's messages or this turn's tool results (earlier model turns don't count), something is cited when tools were used, every cited article or alert comes with its publication date, and links are the url of a retrieved source. A failing draft goes back once with the findings. | `review.js` |
| **Security** | Third-party text (news articles, alert text written from them, custom feed names) passes through a guard. A passage addressed to the assistant ("ignore previous instructions…") is replaced with `[removed: …]` before the model sees it and recorded as a flag on the step and the audit. The scanner withholds such articles entirely (`articlesWithheld`) and fences article text in `<article>` tags. Before that, each new article also goes to Model Armor on Google Cloud (template `exportmate-untrusted-text`: prompt injection and jailbreak at medium confidence and above, malicious links), which catches reworded injections the patterns miss; the article is withheld with what matched (`model armor: …`). If Model Armor can't screen an article it is not recorded, so the next scan tries again, and `scan.armor_failed` is logged; it is never let through unscreened. The `untrusted-content` and `scope` rules tell the model tool results are data, and not to role-play or reveal its instructions. Least privilege: read-only tools, so an injected instruction has nothing to trigger. Feed URLs are HTTPS-only with private and metadata addresses blocked; chats are rate-limited per client and per instance; source changes need an owner or editor token. | `guard.js`, `armor.js`, `scan.js`, `feeds.js`, `index.js` |
| **Evaluation** | Unit tests for every deterministic part (CI). A golden set of 18 cases (simple, multi-hop, tool use, follow-up, hallucination traps, edge cases, security and scope probes) with expected figures computed from the live stock; a case can carry the browser demo's orders and playbook (`demo`), passed through the same checks as a demo chat. Each case is scored on the answer, the trajectory (tools and arguments), the auditor's checks and, optionally, an LLM judge (faithfulness, relevance, rubric). Each run is saved and compared with the previous one; it exits 1 on a regression. The news scan has its own labeled set (`eval/scan-golden.js`): 19 articles written for the eval, half real links to the stock (HS code, market, timber origin, missing geolocation) and half traps (other commodities, exchange rates, fuel, measures on other goods from Vietnam), plus two reports of one event. Each article is scored on whether it was kept, the SKUs named (required and allowed, computed from the stock), severity and direction; a run reports relevance and SKU precision/recall and how often the code checks after Gemini (`relevance.js`) overrode it. `--repeat=N` measures how stable the verdicts are. | `test/`, `eval/` |
| **AgentOps** | Every request has an ID (`X-Request-Id`, stored on the audit). One `chat.completed` JSON log line per answer for Cloud Logging (status, policy version, model, tier, escalated, cached, latency, model calls, tokens, tool errors by kind, revised, failed checks, citations, withheld passages), grouped by Cloud Trace. No question text, tokens or emails in logs. `npm run ops` summarises recent audits: pass rate, revision rate, per-check failures, p50/p95 latency, tokens and tool calls per answer, tool error rates, withheld passages, policy and model versions in use (drift), the router's split between tiers with the share of simple answers escalated, and the cache hit rate. | `log.js`, `index.js`, `metrics.js`, `ops.js` |
| **Explainability** | The audit is the explainability record: question, every plan/tool/draft/review/answer step with arguments and results, citations with dates, checks, policy version, model, tokens, latency. The app shows it under each answer and can download it as JSON. | `agent.js`, `frontend/ai/chat/Audit.tsx` |
| **Memory** | Short-term: the conversation the client sends (last 20 messages). Earlier answers keep the titles they cited but are not a data source (`tools-first` rule; the auditor ignores model turns). Long-term knowledge is the vector index. | `index.js`, `agent.js` |

## Tool registry

| Tool | Scope | Access | Data |
| --- | --- | --- | --- |
| `search_knowledge` | public | read | `kb` vector index: articles, alerts, items, sources, guides |
| `query_inventory` | public | read | `inventory` (synthetic demo stock) |
| `get_alerts` | public | read | `impacts`, `inventory`, `scans` |
| `calculate` | public | none | arithmetic only |
| `get_scan_status` | public | read | `scans`, `sources` |
| `get_company_profile` | company | read | the caller's profile from the backend (`GET /api/v1/company/knowledge` with the user's own token) |
| `query_orders` | orders | read | the company's orders and their market checklists from the backend (`GET /api/v1/trade-map` with the user's own token), or the browser demo's orders sent with the question (each with its one sample rule check; checked and trimmed by `orders.js` `demoMapOrders`, at most 200). Filtered and shaped in `orders.js`. Marked `live`: answers that call it are never cached |
| `get_playbook` | playbook | read | the playbook rules switched on, from the backend (`GET /api/v1/playbook/rules` with the user's own token) or sent by the browser demo (`demoPlaybook`). The `playbook` rule has the agent apply them, citing each, when it advises. Marked `live` |

To add a tool: add an entry to `REGISTRY` in `agent.js` with its declaration, scope and handler. Keep it read-only unless an approval step exists. Add its label in `frontend/ai/chat/Audit.tsx` and a golden case that needs it.

## Working with the harness

```sh
cd ai/server
npm test                               # unit tests, no GCP needed (also in CI)
npm run eval                           # golden set against Gemini + Firestore; saves eval/results/<time>.json
npm run eval -- --only=latest-scan     # selected cases
npm run eval -- --judge                # add the LLM judge (JUDGE_MODEL, default GEMINI_MODEL)
npm run eval -- --tier=simple          # every case on one tier, e.g. to see what the small model can handle
npm run eval:vertex                    # also create an evaluation run on Agent Platform › Evaluation (managed judges)
npm run ops                            # last 7 days of chats; --days=1, --eval, --json
npm run eval:scan                      # news scan relevance on labeled articles; saves to scan_eval_runs
npm run eval:scan -- --repeat=3        # each case 3 times; passes only if it passes every time
```

When the assistant gets something wrong:
1. Find the answer's audit (request ID in the logs, or download it from the app) and see which step failed: retrieval, tool choice, arguments, figures or citation.
2. Add a golden case that reproduces it (`eval/golden.js`).
3. Fix it at the right layer: a tool or its schema, retrieval, an auditor check, or a rule in `policy.js` with its `prevents` line. Examples:
   - Writing the `category-count` case showed that `category: "Plywood"` also matched Hardwood plywood (production answered USD 655,181 instead of 494,053), so category and market are now enums with exact matching.
   - The first eval run on GCP (14/17, 13 Oct 2026) found the agent dropping news dates despite the `dated-evidence` rule, so the auditor now enforces them (`News cited with its date`), and writing a poem despite the `scope` rule, so that rule moved first and names what to decline. The other failure was in the judge, which marked a correct decline as irrelevant; it now grades against the rubric. Next run: 17/17.
4. Run `npm test` and `npm run eval`; no regressions before deploying.

When the scan raises a false alarm or misses an article: add the article (rewritten so it isolates the link or the trap) to `eval/scan-golden.js`, then fix the scan's `RULES` in `scan.js` or the checks in `relevance.js` until `npm run eval:scan` passes.

**Agent Platform evaluation** (`platform/evaluate.py`, Python via `uv`, runs locally, not in the Cloud Run job): `npm run eval:vertex` runs the golden set as usual, then exports each case as Agent Platform agent data (`eval/results/<session>.vertex.json`, git-ignored): the instruction and tool declarations the model was given, earlier turns, every function call with its full response, the auditor's send-back and the final answer. It creates an **evaluation run** with the Gen AI evaluation client (`agentplatform.Client().evals.create_evaluation_run`) scored by managed, Gemini-judged adaptive-rubric metrics: final response quality, tool use quality, hallucination (claims the tool results don't support) and safety. Runs belong to the evaluation experiment **ExportMate assistant** on **Agent Platform › Evaluation**, where each case's rubric verdicts and runs can be compared; results are written to the project's Agent Platform staging bucket (or `EVAL_GCS_DEST`). The service runs in us-central1 (`EVAL_LOCATION`; it isn't offered in asia-southeast1). The runner's own checks (expected tools and arguments, figures, declines) stay in Firestore `eval_runs`; the managed metrics don't replace them.

Eval runs call Gemini and write audits with `channel: "eval"` to the same Firestore project; `npm run ops` leaves them out by default.

## Not done yet

- **Semantic answer cache**: only the same question (after normalising case, spacing and end punctuation) hits the cache; a reworded one is answered again. Matching by embedding would catch rewordings but risks reusing an answer about a different SKU or market, so it needs its own eval first.
- **Learned router**: tiers are chosen by rules. When the audits show which simple-tier answers get escalated or fail, those signals should move into `router.js` (with a golden case each), or a classifier could be trained on the audits.

- **Long-term memory** per company (preferences, recurring questions): not stored. The audits hold history but are not fed back.
- **Cross-encoder reranking**: retrieval uses BM25 over vector candidates, not a learned reranker; there is no relevance floor.
- **PII**: logs carry no question text, but audits store the question and answer as asked, without masking.
- **Guard coverage**: new articles are screened by Model Armor at scan time, but the chat-time guard (alert text, custom feed names) is pattern-based, so a reworded injection there can get past it. Articles indexed before Model Armor was switched on were only checked by the patterns. The user's own messages are not screened. The read-only tools, the auditor's link and figure checks and the prompt rules are the other layers.
- **Scan eval coverage**: the labeled articles are written for the eval, so they are cleaner than real feed snippets; real articles the scan got wrong should be added as users report them. Alerts can't be marked useful or not relevant yet, so there is no measure on live scans.
- **Eval in CI**: the golden sets need GCP credentials and cost model calls, so they run by hand; only the unit tests run in CI.
- **Feedback loop**: users can't rate an answer yet, so failures reach the golden set only through audits and reports.
