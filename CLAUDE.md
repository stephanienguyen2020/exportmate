# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ExportMate: a trade-compliance prototype for small manufacturers (demo persona: a Vietnamese wood-products/furniture exporter). Three independently built parts:

- **Frontend** (`frontend/`): React 19 + TypeScript + Vite SPA, deployed to Vercel (exportmate.vercel.app).
- **Backend** (`backend/`): Python FastAPI + Postgres (Cloud SQL), Firebase Auth tokens, routes under `/api/v1`. Being built in phases; docs are in `backend/docs/`: `REQUIREMENTS.md` (scope, business rules, phases, open questions), `DECISIONS.md` (database, hosting, routing, auth, storage and why), `API.md` (every built and planned endpoint, where the frontend calls it; update it when changing a route), `AI_IDEAS.md` (AI ideas still to decide), `FRONTEND_GAPS.md` (built endpoints the frontend doesn't use yet). Commands and layout: `backend/README.md`.
- **AI service** (`ai/server/`): a plain-JS Node ≥20 HTTP service (no framework, no build step) on Google Cloud Run that serves every `/api/*` route, backed by Firestore and Gemini on Vertex AI.

## Commands

Frontend (`frontend/`):

```sh
npm install
npm run dev       # Vite on http://127.0.0.1:5173, proxies /api to 127.0.0.1:8080
npm run build     # tsc -b type-check + vite build to dist/ (no frontend linter)
npm test          # Vercel proxy test (node --test, Node 22.18+) + Playwright browser tests against mocked APIs
npx playwright test -g "news sources"   # single Playwright test; `npx playwright install chromium` once first
npm run preview
```

AI service (`ai/server/`, needs `gcloud auth application-default login`; talks to the real Firestore of `GOOGLE_CLOUD_PROJECT`, default `exportmate-app` until the move to `skilful-scarab-511320-q9` in `infra/terraform/README.md` is finished):

```sh
npm run dev       # node --watch on :8080
npm run seed      # upsert synthetic inventory + default news sources, then rebuild the vector index
npm run scan      # run one news scan now (--lookback=14 to re-read two weeks)
npm run index     # rebuild the vector index; `node rag.js "<query>"` runs a test search
npm test          # harness unit tests (no GCP needed)
npm run eval      # golden-set eval against live Gemini + Firestore (--only=<ids>, --judge); exits 1 on regressions
npm run eval:vertex # the same, then an Agent Platform evaluation run (managed judges; needs uv, eval/vertex)
npm run eval:scan # news-scan relevance on labeled articles against live Gemini (--only=<ids>, --repeat=N); exits 1 on regressions
npm run ops       # health summary of recent chat audits (--days=1, --json)
PROJECT_ID=skilful-scarab-511320-q9 ./deploy.sh   # Cloud Build image -> Cloud Run service + job (infra in infra/terraform/ai_service.tf)
gcloud run jobs execute exportmate-ai-task --region asia-southeast1 --wait --args="node eval/run.js"   # any npm script's command, on GCP
```

CI (`.github/workflows/ci.yml`, on pushes to main and on PRs) runs the frontend build and `npm test`, backend ruff + `alembic check` + pytest against Postgres, and a parse check plus the unit tests of `ai/server` (the golden-set eval needs GCP and runs by hand). Beyond that, verification is manual headless-Chrome checks at multiple widths; `frontend/docs/VALIDATION.md` records the flows that have been exercised.

Backend (`backend/`, uses uv; Postgres via `docker compose up -d` on :5433):

```sh
uv run alembic upgrade head
uv run python -m app.seed_demo_data --email lan@example.com
uv run python -m app.cleanup_imports --older-than-days 30   # delete uploads never committed
```

## Architecture

### Backend layering (`backend/app/`)

- `api/` routers do HTTP only; `services/` hold business logic and own `db.commit()`; `database/queries/` is the only place that builds SQL (never commits); `database/models/` holds tables; `schemas/` are pydantic models (camelCase JSON); `core/` has config, auth, errors.
- Company scoping: routes take `ViewerContext`/`EditorContext`/`OwnerContext` (from `core/auth.py`); the company comes from the caller's Postgres membership, never the request. Other companies' records return 404.
- Team (`services/members.py`, `api/members.py`, frontend `src/Team.tsx` on the Account page): owners invite an email address with a role (`company_invites`, emailed via `core/email.py`, 14 days, renewed by inviting again), change roles and remove members; anyone leaves. The invitee sees it at onboarding (`GET /me/invites`, matched on the Firebase-verified email) and joins instead of creating a company. A company always keeps one owner (`409 last_owner`, memberships locked); one company per user (`409 already_in_company`). Audited as `member.*`. Tests put people in a company directly with `conftest.add_member`.
- Money is an integer number of hundredths of the currency unit + an ISO 4217 currency (`valueMinor`; also ×100 for JPY/VND, so readers always divide by 100). Orders from CSV import start as `awaiting_analysis`; the import keeps the original file and each row (`import_rows`) so later reports can cite them. Uploads are capped at 4 MB (Vercel's function body limit) and 60 per user per hour (`core/rate_limit.py`, in memory per instance).
- Style the user asked for: all imports at the top of the file, and specific names (`success_response`, `get_order_by_external_id`), not generic ones (`ok`, `get`).
- Relational data belongs in Postgres (Cloud SQL in production), not hard-coded in the frontend. Trade map: shared reference tables (`markets`, `countries`, `ports`, `document_kinds`, `market_requirements`, `satellite_observations`) and company tables (`suppliers`, `supplier_documents`, `company_sites`); orders match suppliers by `name_key` (trimmed, lower-case). `services/trade_map.py` places destinations, checks documents per market and compares a market, a ship date, or a route. Editors add, edit and delete suppliers (with their documents) and sites from the map (`/suppliers`, `/sites`; `services/suppliers.py`, `services/company_sites.py`): a site's `site_key` comes from its name and never changes (observations cite it), and at most one site is the route origin. Checklist lines carry HS prefixes (wood, food, textiles, electronics), optional effective and change dates, and a route-sensitive flag for origin proofs. Seed data lives in `app/seed_data/*.json`: `python -m app.seed_reference_data` (run by `deploy.sh` after migrations) and `seed_demo_data` (demo company's suppliers/sites). Every market requirement cites an official text (`regulation_document_id` + `source_quote`): the reference seed downloads the texts in `app/seed_data/regulation_sources.json` once into shared regulations (`regulations.company_id` null, read-only for companies). Observations are samples.
- Reports (`services/reports.py`, `api/reports.py` under `/report-drafts`, frontend `src/Reports.tsx` at `#/workspace/reports`): an order report (its checklist via `trade_map.build_order_checklist`, cited texts, CSV row) or a company report (checklist changes ahead, News watch alerts fetched from the AI service with the caller's token by `core/news_alerts.py`, floods near suppliers/sites, new regulation versions, orders with gaps, suppliers). Generated into a `report_drafts` row visible only to its author, with `original` and editable `content`; edits may change any text or row but not the section structure, and the PDF (fpdf2 + bundled Noto Sans in `app/assets/fonts`, needed for Vietnamese) shades every line that differs from `original`. `POST /report-drafts/{id}/email` (editor, ≤5 recipients, `REPORT_EMAILS_PER_HOUR`) sends via Resend (`core/email.py`; sandbox without `RESEND_API_KEY`), locks the draft and audits `report.emailed`.
- News watch ↔ orders (`services/news_matches.py`, `api/news_matches.py` under `/news-matches`, frontend `frontend/ai/news/NewsOrders.tsx` + `news-matches.ts`): News watch matches articles to sample stock, never to orders, so the backend suggests open orders sharing an HS heading and market with a stock item an alert names (stock from the AI service's `/api/inventory`), and an owner or editor confirms or rejects each one, or links an order that wasn't suggested (`news_order_reviews`, keyed by the alert's ID, with a copy of its headline; audited `news.reviewed` / `news.review_cleared`). Only confirmed links are treated as fact: the company report names them beside each alert. The browser demo makes the same suggestions in `news-matches.ts` and keeps verdicts in localStorage `em-news-reviews`.
- Order status: an analysis run sets it, and an owner or editor can set it by hand with a required note (`PATCH /orders/{id}/status`, Status panel `frontend/src/OrderStatus.tsx` on the order's page). Every change, manual or by a run, is a row in `order_status_changes` (shown as the order's history); manual ones are audited as `order.status_changed`. Status labels, colours and which may be set by hand live in `order_statuses` (seeded from `reference.json` `orderStatuses`, served by `GET /order-statuses`), and the live workspace reads them from there.
- Analysis (phase 2, backend only so far): `services/analysis.py` runs in code inside `POST /runs`: the trade map's check, cost lines from the rule's duty rate or cost settings (`services/cost_settings.py`), checked playbook rules (`services/rule_checks.py`: WHEN/THEN as data, one checker), a suggested action and an audit; it saves one report per order (content as JSON) and sets order statuses. A duty whose rate changes by the ship date (`changes_on`) is listed unpriced. The order report draft (`services/reports.py`) repeats the order's latest analysis; preparing a report never runs one. Supplier documents typed in the map and confirmed from an upload are one record (number, issuer, expiry; editing keeps `upload_id`). AI (Gemini via `core/gemini.py`, JSON with a fixed schema and embeddings; tests use `FakeGemini` in `conftest.py`, with word-hashing vectors) reads uploaded supplier documents (`services/supplier_documents.py`), drafts a company's market requirements from its own regulation (`services/market_requirements.py` + `services/document_text.py`: PDF/HTML text, long texts cut to the closest sections; the owner reviews; only reviewed requirements in a version without drafts are in force, `list_requirements_in_force`) and suggests HS codes (`services/hs_suggestions.py`: past orders by `pg_trgm`, official tariff lines `hs_headings` by pgvector, seeded from `seed_data/hs_headings.json` built by `scripts/build_hs_headings.py`). Postgres needs the `pgvector/pgvector:pg16` image. Code checks every AI answer before saving.
- Suggested solutions (`services/solutions.py`, `api/solutions.py`, frontend `src/Solutions.tsx` on an order's analysis report): each gap in a report (market + requirement key + `missing`/`mismatch`) is a problem; Gemini writes a summary and steps from the report's facts, the cited text and the company's notes on earlier solutions to the same problem (code checks every number and link against what it was given). Solutions are saved (`solutions`) and offered for later orders with the same problem, and every saved one is listed by problem in the Knowledge base tab (`GET /solutions`, `src/KnowledgeBase.tsx` at `#/workspace/knowledge`, reusing `SolutionCard`; read, note, adopt or reject there, use only from an order's report); people add append-only notes (`solution_notes`), adopt or reject, and record which one an order follows (`solution_uses`). A solution expires after `valid_until` (`SOLUTION_VALID_DAYS`, or the day before the requirement's `changes_on`), or when the requirement cites another regulation version or leaves the checklist (worked out on each read); expired ones are listed for reference, never the default, can't be used or adopted, and "Analyse again" writes a new one with `supersedes_id`. Every write is audited (object type `solution`).
- Actions (phase 3, backend only so far): an analysis report can lead to a supplier message when `services/report_review.message_blocked_reason` allows it (latest report, not blocked, audit passed, owner-reviewed if a rule asked, something missing); `services/supplier_messages.py` drafts it with Gemini (English, report facts only, checked for the order ID and cited links), then draft → approved (owner, hash of recipient + subject + body) → sent once via `core/email.py`; edits after approval reset it to draft. Suppliers have `contact_name` / `contact_email`. Also report feedback, the owner's audit log (`GET /audit-events`) and the public contact form (`POST /contact` → `CONTACT_INBOX`). English everywhere for now.
- Logging (`core/logging.py`): every line carries the request ID; one `request.completed` line per request with user/company IDs; services log what they changed with `extra={...}`. JSON in production for Cloud Logging. Never log tokens, emails or file contents.

### Frontend routing and state

- Hash-based routing, no router library. `frontend/src/main.tsx` holds `Root` (public pages, account flows, session gate that redirects to `#/login` and remembers the target) and `App` (the workspace under `#/workspace/...`; the route string has the `workspace/` prefix stripped and views are selected with `route === "orders"` etc.). Most workspace views live inline in `main.tsx`.
- `frontend/src/Landing.tsx` is the public landing (`#/`); `frontend/src/TradeGlobe.tsx` is a Three.js globe that is lazy-loaded into its own chunk (Vite's 500 kB chunk warning for it is expected). The Firebase SDK and PapaParse are also loaded on demand, keeping the main chunk under 500 kB.
- Trade map (`#/workspace/map`, deep links `map/order/<id>`, `map/market/<code>`, `map/supplier/<name>`): `frontend/src/TradeMap.tsx` is lazy-loaded. Its world view uses `TradeMapGlobe.tsx` (Three.js, OrbitControls, world-atlas texture, elevated arcs and animated route particles); regional views and the optional 2D world view use d3-geo (110m for the world, 50m on demand for regional views). The globe has pause/zoom/reset controls, reduced-motion support and a WebGL fallback. Editors add and edit suppliers and sites in the side panel; while a form is open the map is 2D and a click sets the location (`projection.invert`) and suggests the country. Routes use a site marked `isRouteOrigin` when one exists; otherwise the world view draws an approximate start from the company profile's named origin (Vietnam, Singapore, Indonesia or Thailand) and says that point is not a recorded site. Connections are illustrative, not vessel tracking. The compare ("What if") panel can save a what-if with a note (`ScenarioNotes.tsx`, `/trade-map/scenarios`, `services/scenarios.py`): a proposal on record that changes nothing on the order, with the comparison stored as it stood; an editor can start the note from a Gemini reading of the comparison (`/suggest`, points checked against the comparison's lines, not saved). All map data comes from the backend (`GET /api/v1/trade-map`, `GET /api/v1/trade-map/compare`), so the map only works in a connected session; the browser-only demo shows a sign-in prompt instead. Only map geometry (projections, camera presets, label placement) lives in the frontend.
- `frontend/src/Account.tsx` + `frontend/src/account-store.ts` + `frontend/src/auth.ts`: sign-up, sign-in, email verification and password reset use Firebase Auth (SDK loaded on first use, and preloaded on the sign-in pages so the "Continue with Google" popup isn't blocked; Google is hidden in dev auth mode and needs the OAuth client in `infra/terraform/README.md`). With `VITE_AUTH_MODE=dev` the Vite dev server accepts any password and sends `dev:<email>` tokens. "Explore the demo" opens the browser-only sample workspace with no account. After sign-in (or the demo), `intendedRoute()` returns to the workspace page that sent the visitor to `#/login`.
- Two kinds of session (`em-session` in sessionStorage): `demo` keeps orders, playbook rules, profile and demo state in browser storage (localStorage: `em-orders`, `em-rules`, `em-sent`, `em-demo-profile`); `api` reads and writes them through the backend (`frontend/src/api.ts`), and `em-profile` is only a cache of `GET /me` (and of the email awaiting verification), removed on sign-out. `getProfile`/`putProfile` pick the key by session, so an account's details never show in the demo. Other sessionStorage keys: `em-next` (page to return to), `em-chat` and `em-chat-session` (chat history and audit session, cleared on sign-out and sign-in). The first-visit workspace tour (`frontend/src/Tour.tsx`: a spotlight on each sidebar item via `data-tour` attributes, skippable, replayed from the ? in the top bar) shows once per browser (localStorage `em-tour-done`); `playwright.config.ts` sets that key so the tour doesn't cover other tests, and `tests/tour.spec.ts` clears it. Seed data is in `frontend/src/data.ts`, with the demo's one sample rule change (`sampleObligation`, `sampleSuppliers`, `sampleCheck`, `sampleCosts`): every demo order, imported ones included, is checked against it, and the demo's counts, costs and dates are worked out from the orders and today's date (seed ship dates count from today). The demo's CSV checks (`frontend/src/order-csv.ts`) mirror the backend's. The AI service reads a signed-in company's orders and playbook rules (`query_orders`, `get_playbook`) with the user's token; a demo chat request carries the demo's orders (each with its sample check) and switched-on rules (`demoWorkspace()` in `frontend/ai/chat/agent-client.ts`).
- The "five-agent review" / rule-change demo in the workspace is simulated client-side for the browser demo only; it is unrelated to the real agent in `ai/server`.
- Phase 2/3 screens for a signed-in company (each lazy-loaded): `frontend/src/Analysis.tsx` (Orders page "Analyse orders" run panel; on an order's page its latest analysis report from `latestReportId`, owner review, feedback, HS code suggestions for an order without a code, and supplier messages drafted → approved → sent), `CompanySettings.tsx` (Account: cost settings, owner-only activity log: the latest 10 events, the whole log as a CSV from `GET /audit-events/export`), `Playbook.tsx` (WHEN/THEN rule builder from `GET /playbook/fields`), requirement drafting and review on a regulation's page (`Regulations.tsx`), certificate upload in the trade map's supplier panel. The landing contact form posts to `POST /api/v1/contact` without a token.

### AI code (`ai/`)

- `frontend/ai/chat/` and `frontend/ai/news/` are frontend TSX modules imported by `frontend/src/main.tsx` (and included in `frontend/tsconfig.json`), not a separate app. `frontend/ai/chat/agent-client.ts` defines the shared API types (`Audit`, `AuditStep`, `Citation`) and the base URL (`VITE_CHAT_API_URL`, default `/api`).
- `ai/server/index.js`: raw `http` server with manual route dispatch (`/api/chat` streams NDJSON; also `/api/audits`, `/api/inventory`, `/api/impacts`, `/api/scan`, `/api/sources`). Config via env: `PORT`, `GEMINI_MODEL_SIMPLE` / `GEMINI_MODEL_COMPLEX` (the assistant's two tiers, default gemini-3.5-flash-lite / gemini-4-argon, see `models.js`; `GEMINI_THINKING_SIMPLE` / `GEMINI_THINKING_COMPLEX` set their thinking levels, default LOW / MEDIUM), `GEMINI_MODEL` (news scan and eval judge, default gemini-3.5-flash), `EMBED_MODEL`, `ALLOWED_ORIGINS`, `SCHEDULER_SA`, `SCAN_AUDIENCE`, `GOOGLE_CLOUD_PROJECT`, `BACKEND_URL` (company backend origin, default `http://127.0.0.1:8000`), `CHAT_LIMIT_PER_CLIENT` / `CHAT_LIMIT_PER_INSTANCE` (chats per hour, default 40 / 200, counted in memory; the client is the first `X-Forwarded-For` address), `SCAN_SCHEDULE` (how the assistant describes the scheduler job), `MODEL_ARMOR_TEMPLATE` (full template name; unset turns Model Armor off). For a chat with a `Bearer` token (signed-in company workspace), `index.js` fetches `GET /api/v1/company/knowledge` with that token and passes the profile to the agent; failures fall back to the anonymous demo chat. News sources (`access.js`): built-in sources are shared by every workspace, and a company can switch one off only for itself (`companySources/{companyId}`); a custom source belongs to the company that added it, and only that company sees it and the articles and alerts it brought in (scan records carry `sourceIds` / `sourceCompanyIds`). Changing sources and starting a manual scan call `GET /api/v1/me` with the caller's token (cached for a minute) and accept only owners and editors (401 signed out, 403 other roles, 503 if the backend can't be reached). Reads take an optional token to apply the company's view. An audit made in a company workspace needs that company's token; the model's raw `thought` stays in Firestore and is never sent to clients. Request bodies over 100 KB get 413 (`limits.js`).
- `agent.js`: a Google ADK (`@google/adk`) `LlmAgent` on Gemini, run per turn by a `Runner` over an in-memory session (the client sends the conversation); ReAct loop (max 6 steps, counted in ADK's model callbacks) over a tool `REGISTRY`, each entry wrapped as an ADK tool that calls the gateway: `search_knowledge`, `query_inventory`, `get_alerts`, `calculate`, `get_scan_status`, and scoped tools, offered and allowed only when the gateway's ctx has their `scope` (policy rules with `when` use the same names): `get_company_profile` (scope `company`, when a company profile was loaded; the system prompt then names that company and flags stock/alerts as demo data; cited as type `company`), `query_orders` (scope `orders`: the company's orders with their market checklists, read from `GET /api/v1/trade-map` with the user's own token, or the browser demo's orders sent with the question and checked by `orders.js` `demoMapOrders`; cited as type `order`, with each check's official text as type `regulation` deep-linking to its document version) and `get_playbook` (scope `playbook`: the switched-on rules from `GET /api/v1/playbook/rules`, or the demo's; cited as type `playbook`). `index.js` passes a `backend` reader for company chats and the client's `demo` data otherwise; a company chat never uses what the client sends. All tools are read-only. Every fact must carry a numbered citation. Each answer streams steps live and is stored as an audit record in the `audits` collection (with `policyVersion`, `requestId`, guard `flags`; `status` is `needs_review` when the final answer still fails the auditor). When changing tools or step shapes, keep `AuditStep` in `agent-client.ts` and the `Audit.tsx` renderer in sync. The harness around it (see `docs/AGENT_HARNESS.md`), all pure modules with tests in `test/`:
  - `policy.js`: the system-prompt rules; each names the failure it `prevents`. Add a rule (and a golden case) when a new failure is found; `POLICY_VERSION` is stored on audits.
  - `gateway.js`: every tool call is validated against its declared schema, scope-checked, budgeted per turn, timed out and retried only on transient errors; refusals return an `errorKind`. `withRetry` also wraps Gemini calls.
  - `guard.js`: third-party text (articles, alerts, custom feed names) addressed to the assistant is replaced with `[removed: …]` and flagged; `asData` fences text placed in prompts.
  - `review.js`: the auditor; citations resolve, figures and percentages appear in the user's messages or this turn's tool results, cited news carries its date, links are retrieved sources. A failing draft goes back once.
  - `router.js`: picks the model tier per question by rules (follow-up, several SKUs, arithmetic, trade rules, judgement, pasted text, injection, length → complex; else simple); `test/router.test.js` pins a tier for every golden case, so a new case must pick one. A simple-tier draft the auditor sends back is revised on the complex model. Models and thinking levels are in `models.js`.
  - `answer-cache.js`: the answer cache's key (normalised conversation, company, switched-off sources, policy, models, date, fingerprint of the tools' data) and which audits may be reused; `agent.js` reads and writes `answer_cache` in Firestore. Mark a tool `live: true` if it reads data outside that fingerprint (answers that call it aren't cached). Evals bypass the cache.
  - `rerank.js`: BM25 rerank of vector candidates (hybrid retrieval). `calc.js`: the calculator. `metrics.js`: audit aggregates for `ops.js` and the eval. `log.js`: JSON log lines on Cloud Run (one `chat.completed` per answer; never question text or tokens).
  - `eval/`: `golden.js` (cases with expectations computed from the live stock), `score.js` (answer + trajectory scoring), `run.js` (runner, optional LLM judge, regression check; results in the git-ignored `eval/results/`). `npm run eval:vertex` (`run.js --vertex`) also creates an Agent Platform evaluation run (`eval/vertex/vertex_eval.py`, a `uv` project using `agentplatform.Client().evals`): each case is exported as agent data (instruction, tool declarations, function calls and responses, answer; `runAgent` returns them as `trace` with `withEvidence`) and judged by managed metrics (final response quality, tool use quality, hallucination, safety). Runs go to the evaluation experiment "ExportMate assistant" on Agent Platform › Evaluation, in us-central1; local only, the Cloud Run image has no Python. `scan-golden.js` / `scan-score.js` / `scan-run.js` do the same for the news scan's relevance judgment (labeled articles, relevance and SKU precision/recall, runs in `scan_eval_runs`).
- `rag.js`: Firestore vector search over `gemini-embedding-001` (768-dim, cosine) in the `kb` collection, indexing stock items, articles, alerts, sources and help guides (`seed/guides.js`); `search()` fetches 3× candidates and reranks them with `rerank.js`.
- `scan.js` + `feeds.js`: news scan — reads enabled RSS/Atom sources, skips already-analysed articles, asks Gemini which SKUs each article affects, writes `impacts` and indexes new articles/alerts. Article text is fenced in `<article>` tags; articles containing injected instructions or malicious links are withheld (`articlesWithheld`): `guard.js`'s patterns first, then Model Armor (`armor.js`, template from Terraform) when `MODEL_ARMOR_TEMPLATE` is set. An article Model Armor couldn't screen isn't recorded, so the next scan retries it (`articlesUnscreened`, `scan.armor_failed`). Triggered daily by Cloud Scheduler (OIDC-signed `POST /api/scan`, which bypasses the 10-minute cooldown); "Scan now" needs an owner or editor. A `locks/scan` document claimed in a Firestore transaction keeps two scans from running at once. After Gemini, `relevance.js` `decide()` keeps an article only if it names a SKU in stock, isn't a repeat of another article and doesn't name another commodity without wood goods; `npm run eval:scan` scores this path. Feeds must be public HTTPS; `feeds.js` checks the address when the socket connects (so DNS rebinding can't reach private or metadata addresses; NAT64/6to4 addresses are judged by the IPv4 inside) and stops reading past 3 MB.
- `db.js`: Firestore client and collection handles (`inventory`, `sources`, `articles`, `impacts`, `scans`). The `kb` and `audits` collections are accessed from `rag.js` and the agent/server code.

### Deployment wiring

- `frontend/vercel.json` rewrites `/api/*` to the Cloud Run URL; locally `frontend/vite.config.ts` proxies `/api` to `:8080`.
- `frontend/.vercelignore` excludes `ai/server` and `docs` from the Vercel upload; `ai/server/.gcloudignore` governs the Cloud Run source deploy.

## Docs

`docs/AI_GUIDE.md` explains how to use the assistant and News watch and how they work (update it with user-visible AI changes). `docs/AGENT_HARNESS.md` maps the AI service's harness (policy, tools, guard, auditor, eval, ops, governance) to code and lists what is not done. Frontend and site planning docs are in `frontend/docs/` (`FRONTEND_PLAN.md`, `ACCOUNT_AND_SITE_PLAN.md`, `LANDING_DESIGN.md`, `VALIDATION.md`, `FIXES.md`); backend docs are in `backend/docs/`. Plans describe intended designs; much of `backend/docs/BACKEND_PLAN.md` (real auth, durable server storage, notification delivery, document extraction) is not implemented. All legal/regulatory content is illustrative; inventory is synthetic, news is real.

Regulations: `frontend/src/Regulations.tsx` implements the library, version history, metadata, authenticated downloads and editor/owner uploads for the built regulation APIs. Map citations deep-link to exact document versions. The Vercel project root is `frontend/`; run Vercel CLI from the repository root. Main is protected; changes go through PRs and all three CI jobs.
