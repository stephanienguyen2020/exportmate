# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ExportMate: a trade-compliance prototype for small manufacturers (demo persona: a Vietnamese wood-products/furniture exporter). Three independently built parts:

- **Frontend** (`frontend/`): React 19 + TypeScript + Vite SPA, deployed to Vercel (exportmate.vercel.app).
- **Backend** (`backend/`): Python FastAPI + Postgres (Cloud SQL), Firebase Auth tokens, routes under `/api/v1`. Being built in phases; docs are in `backend/docs/`: `REQUIREMENTS.md` (scope, business rules, phases, open questions), `DECISIONS.md` (database, hosting, routing, auth, storage and why), `API.md` (every built and planned endpoint, where the frontend calls it; update it when changing a route), `AI_IDEAS.md` (AI ideas still to decide), `FRONTEND_GAPS.md` (built endpoints the frontend doesn't use yet). Commands and layout: `backend/README.md`.
- **AI service** (`ai/server/`): plain JS on Node ≥20 (no framework, no build step), one image with two servers: the API on Google Cloud Run that serves every `/api/*` route (`index.js`), and the assistant's ADK multi-agent team on Gemini Enterprise Agent Platform's Agent Runtime (`runtime.js`), with Agent Platform Sessions, Memory Bank, RAG Engine, Evaluation and Govern (Agent Identity, Agent Registry, Agent Gateway, Model Armor). Data is in Firestore; models are Gemini.

## Commands

Frontend (`frontend/`):

```sh
npm install
npm run dev       # Vite on http://127.0.0.1:5173, proxies /api to 127.0.0.1:8080
npm run build     # tsc -b type-check + vite build to dist/ (no frontend linter)
npm test          # Vercel proxy test (node --test, Node 22.18+) + Playwright browser tests against mocked APIs
npx playwright test -g "news sources"   # single Playwright test; `npx playwright install chromium` once first
npm run preview
```

AI service (`ai/server/`, needs `gcloud auth application-default login`; talks to the real Firestore of `PROJECT_ID` or `GOOGLE_CLOUD_PROJECT`, default `skilful-scarab-511320-q9`; the website's AI service and its data moved there from `exportmate-app`, see `infra/terraform/README.md`):

```sh
npm run dev       # node --watch on :8080; reads ai/server/.env if present (.env.example: AGENT_RUNTIME = a dev instance turns on Sessions + Memory Bank locally)
npm run seed      # upsert synthetic inventory + default news sources, then rebuild the vector index
npm run scan      # run one news scan now (--max-age=N sets the age rule for this run; 0 = any age)
npm run index     # rebuild the RAG Engine index (RAG_BUCKET); `node rag.js "<query>"` runs a test search
npm run runtime   # the agents behind the Agent Runtime contract on :8080 (PORT); AGENTS_AT=http://127.0.0.1:8080 points the API at it
npm test          # harness unit tests (no GCP needed)
npm run eval      # golden-set eval against live Gemini + Firestore (--only=<ids>, --judge, --tier=, --engine = the deployed agents); exits 1 on regressions
npm run eval:vertex  # the same, then an evaluation run on Agent Platform › Evaluation (platform/evaluate.py, needs uv)
npm run eval:scan # news-scan relevance on labeled articles against live Gemini (--only=<ids>, --repeat=N); exits 1 on regressions
npm run ops       # health summary of recent chat audits and news scans (--days=1, --json)
PROJECT_ID=skilful-scarab-511320-q9 ./deploy.sh   # Cloud Build image -> Cloud Run service + job + Agent Runtime (GATEWAY=…, AGENTS=0 to skip)
uv run --project platform python platform/runtime.py show|create|deploy|delete   # the Agent Runtime instance (Sessions, Memory Bank, container, Agent Identity)
PROJECT_ID=… RUNTIME=… ../../infra/agent-platform/govern.sh   # owner: Agent Identity roles, Agent Registry, egress IAM, Agent Gateway + Model Armor (ENFORCE=1 to block)
gcloud run jobs execute exportmate-ai-task --region asia-southeast1 --wait --args="node eval/run.js"   # any npm script's command, on GCP
```

Monitoring (`infra/monitoring/`, per service, safe to re-run): log-based metrics, an email channel, an uptime check, alert policies and a dashboard from the JSON files in `ai/` and `backend/`:

```sh
PROJECT_ID=skilful-scarab-511320-q9 PART=ai SERVICE=exportmate-ai ALERT_EMAIL=… infra/monitoring/apply.sh
PROJECT_ID=skilful-scarab-511320-q9 PART=backend SERVICE=exportmate-backend WEBSITE_HOST=exportmate.vercel.app ALERT_EMAIL=… infra/monitoring/apply.sh
```

CI (`.github/workflows/ci.yml`, on pushes to main and on PRs) runs the frontend build and `npm test`, backend ruff + `alembic check` + pytest against Postgres, and a parse check plus the unit tests of `ai/server` (the golden-set eval needs GCP and runs by hand). Beyond that, verification is manual headless-Chrome checks at multiple widths; `frontend/docs/VALIDATION.md` records the flows that have been exercised.

## Architecture

### Backend layering (`backend/app/`)

- `api/` routers do HTTP only; `services/` hold business logic and own `db.commit()`; `database/queries/` is the only place that builds SQL (never commits); `database/models/` holds tables; `schemas/` are pydantic models (camelCase JSON); `core/` has config, auth, errors.
- Company scoping: routes take `ViewerContext`/`EditorContext`/`OwnerContext` (from `core/auth.py`); the company comes from the caller's Postgres membership, never the request. Other companies' records return 404.
- Team (`services/members.py`, `api/members.py`, frontend `src/Team.tsx` on the Account page): owners invite an email address with a role (`company_invites`, emailed via `core/email.py`, 14 days, renewed by inviting again), change roles and remove members; anyone leaves. The invitee sees it at onboarding (`GET /me/invites`, matched on the Firebase-verified email) and joins instead of creating a company. A company always keeps one owner (`409 last_owner`, memberships locked); one company per user (`409 already_in_company`). Audited as `member.*`. Tests put people in a company directly with `conftest.add_member`.
- Money is an integer number of hundredths of the currency unit + an ISO 4217 currency (`valueMinor`; also ×100 for JPY/VND, so readers always divide by 100). Orders from CSV import start as `awaiting_analysis` and the commit analyses them straight away (`analysis.start_run` on the new orders; if it fails the orders stay saved and awaiting); the import keeps the original file and each row (`import_rows`) so later reports can cite them. Uploads are capped at 4 MB (Vercel's function body limit) and 60 per user per hour (`core/rate_limit.py`, in memory per instance).
- Style the user asked for: all imports at the top of the file, and specific names (`success_response`, `get_order_by_external_id`), not generic ones (`ok`, `get`).
- Relational data belongs in Postgres (Cloud SQL in production), not hard-coded in the frontend. Trade map: shared reference tables (`markets`, `countries`, `ports`, `document_kinds`, `market_requirements`, `satellite_observations`) and company tables (`suppliers`, `supplier_documents`, `company_sites`); orders match suppliers by `name_key` (trimmed, lower-case). `services/trade_map.py` places destinations, checks documents per market and compares a market, a ship date, or a route. Adding, renaming or deleting a supplier, or changing its documents, analyses the orders that name it again (`analysedOrderIds`; confirming an uploaded certificate doesn't yet). Editors add, edit and delete suppliers (with their documents) and sites from the map (`/suppliers`, `/sites`; `services/suppliers.py`, `services/company_sites.py`): a site's `site_key` comes from its name and never changes (observations cite it), and at most one site is the route origin. Checklist lines carry HS prefixes (wood, food, textiles, electronics), optional effective and change dates, and a route-sensitive flag for origin proofs. Seed data lives in `app/seed_data/*.json`: `python -m app.seed_reference_data` (run by `deploy.sh` after migrations) and `seed_demo_data` (demo company's orders, suppliers/sites; it then analyses orders with no report, as an import does, so statuses and reports come from the analysis). Every market requirement cites an official text (`regulation_document_id` + `source_quote`): the reference seed downloads the texts in `app/seed_data/regulation_sources.json` once into shared regulations (`regulations.company_id` null, read-only for companies). Observations are samples.
- Reports (`services/reports.py`, `api/reports.py` under `/report-drafts`, frontend `src/Reports.tsx` at `#/workspace/reports`): an order report (its checklist via `trade_map.build_order_checklist`, cited texts, CSV row) or a company report (checklist changes ahead, News watch alerts fetched from the AI service with the caller's token by `core/news_alerts.py`, floods near suppliers/sites, new regulation versions, orders with gaps, suppliers). Generated into a `report_drafts` row visible only to its author, with `original` and editable `content`; edits may change any text or row but not the section structure, and the PDF (fpdf2 + bundled Noto Sans in `app/assets/fonts`, needed for Vietnamese) shades every line that differs from `original`. `POST /report-drafts/{id}/email` (editor, ≤5 recipients, `REPORT_EMAILS_PER_HOUR`) sends via Resend (`core/email.py`; sandbox without `RESEND_API_KEY`), locks the draft and audits `report.emailed`.
- News watch ↔ orders (`services/news_matches.py`, `api/news_matches.py` under `/news-matches`, frontend `frontend/ai/news/NewsOrders.tsx` + `news-matches.ts`): News watch matches articles to the company's goods (AI service `goods.js`: what its profile names and its orders ship, each with an HS code and markets), never straight to orders, so the backend suggests open orders by walking the knowledge graph (`services/knowledge_graph.py`): from what the article names (alert `mentions`: materials, HS codes, origin countries, markets) through suppliers' sourcing (`supplier_sourcing`) and the material chain (`graph_nodes`, `graph_edges`, a recursive SQL walk; data and its builder in `app/knowledge_graph/`, loaded by the reference seed), and from each item an alert names (same HS heading and market; from the AI service's `/api/inventory`, read with the caller's token). Each suggestion carries its `path`, every link citing its source. Suppliers' sourcing is entered with the supplier on the trade map ("Materials it buys", `services/supplier_sourcing.py`) or accepted from what AI read on an uploaded certificate; the words articles and documents use are matched to graph nodes by `services/graph_words.py` (species, broad words such as "timber", chain products such as "plywood"). An owner or editor confirms or rejects each suggestion, or links an order that wasn't suggested (`news_order_reviews`, keyed by the alert's ID, with a copy of its headline and the way and path it was found by, which `GET /news-matches/accuracy` counts; audited `news.reviewed` / `news.review_cleared`). Only confirmed links are treated as fact: the company report names them beside each alert. The browser demo makes the same suggestions in `news-matches.ts` and keeps verdicts in localStorage `em-news-reviews`.
- Editing and removing an order (`PATCH` / `DELETE /orders/{id}`, editor; `services/orders.py`, frontend `src/workspace/OrderFacts.tsx` on the order's page, live and demo through `store.ts` `saveOrder` / `removeOrder`): every field but the ID (reports, solutions and the audit log name the order by it), with the CSV's rules (`OrderUpdate` reuses `order_csv.py`'s limits; the form uses `order-csv.ts` `orderCellErrors`). A change is audited as `order.updated` (from/to per field) and the order is analysed again; removing cascades to its history, reports, supplier messages, HS suggestions, what-ifs and news reviews and audits `order.deleted` with what the order was.
- Order status: an analysis run sets it, and an owner or editor can set it by hand with a required note (`PATCH /orders/{id}/status`, Status panel `frontend/src/OrderStatus.tsx` on the order's page), or for several orders at once with one note (`PATCH /orders/status`, all or none, at most `MAX_STATUS_CHANGE_ORDERS`; `BulkStatusBar` in the same file, shown on the Orders page when orders are ticked). Every change, manual or by a run, is a row in `order_status_changes` (shown as the order's history); manual ones are audited as `order.status_changed`. Missing data (HS code, market checklist, supplier record) makes an order `exposed` with that data as its next step; `needs_data` is `retired` in `order_statuses` (named only in earlier history, never a filter or a choice). Status labels, colours and which may be set by hand live in `order_statuses` (seeded from `reference.json` `orderStatuses`, served by `GET /order-statuses`), and the live workspace reads them from there.
- Analysis (phase 2, backend only so far): `services/analysis.py` runs in code inside `POST /runs`: the trade map's check, cost lines from the rule's duty rate or cost settings (`services/cost_settings.py`), checked playbook rules (`services/rule_checks.py`: WHEN/THEN as data, one checker), a suggested action and an audit; it saves one report per order (content as JSON) and sets order statuses. A duty whose rate changes by the ship date (`changes_on`) is listed unpriced. The order report draft (`services/reports.py`) repeats the order's latest analysis; preparing a report never runs one. Supplier documents typed in the map and confirmed from an upload are one record (number, issuer, expiry; editing keeps `upload_id`). AI (Gemini via `core/gemini.py`, JSON with a fixed schema and embeddings; tests use `FakeGemini` in `conftest.py`, with word-hashing vectors) reads uploaded supplier documents (`services/supplier_documents.py`), drafts a company's market requirements from its own regulation (`services/market_requirements.py` + `services/document_text.py`: PDF/HTML text, long texts cut to the closest sections; the owner reviews; only reviewed requirements in a version without drafts are in force, `list_requirements_in_force`) and suggests HS codes (`services/hs_suggestions.py`: past orders by `pg_trgm`, official tariff lines `hs_headings` by pgvector, seeded from `seed_data/hs_headings.json` built by `scripts/build_hs_headings.py`). Postgres needs the `pgvector/pgvector:pg16` image. Code checks every AI answer before saving.
- Suggested solutions (`services/solutions.py`, `api/solutions.py`, frontend `src/Solutions.tsx` on an order's analysis report): each gap in a report (market + requirement key + `missing`/`mismatch`) is a problem; Gemini writes a summary and steps from the report's facts, the cited text and the company's notes on earlier solutions to the same problem (code checks every number and link against what it was given). Solutions are saved (`solutions`) and offered for later orders with the same problem, and every saved one is listed by problem in the Knowledge base tab (`GET /solutions`, `src/KnowledgeBase.tsx` at `#/workspace/knowledge`, reusing `SolutionCard`; read, note, adopt or reject there, use only from an order's report); people add append-only notes (`solution_notes`), adopt or reject, and record which one an order follows (`solution_uses`). A solution expires after `valid_until` (`SOLUTION_VALID_DAYS`, or the day before the requirement's `changes_on`), or when the requirement cites another regulation version or leaves the checklist (worked out on each read); expired ones are listed for reference, never the default, can't be used or adopted, and "Analyse again" writes a new one with `supersedes_id`. Every write is audited (object type `solution`).
- Actions (phase 3, backend only so far): an analysis report can lead to a supplier message when `services/report_review.message_blocked_reason` allows it (latest report, not blocked, audit passed, owner-reviewed if a rule asked, something missing); `services/supplier_messages.py` drafts it with Gemini (English, report facts only, checked for the order ID and cited links), then draft → approved (owner, hash of recipient + subject + body) → sent once via `core/email.py`; edits after approval reset it to draft. Suppliers have `contact_name` / `contact_email`. Also report feedback, the owner's audit log (`GET /audit-events`) and the public contact form (`POST /contact` → `CONTACT_INBOX`). English everywhere for now.
- Logging (`core/logging.py`): every line carries the request ID; one `request.completed` line per request with user/company IDs; services log what they changed with `extra={...}`. JSON in production for Cloud Logging. Never log tokens, emails or file contents.

### Frontend routing and state

- Hash-based routing, no router library. `frontend/src/main.tsx` holds `Root` (public pages, account flows, session gate that redirects to `#/login` and remembers the target). The workspace under `#/workspace/...` is `frontend/src/workspace/`: `Workspace.tsx` is the shell (sidebar, top bar, toast, tour) and picks a page from its `routes` table by the route's first segment (`orders/<id>` passes the rest as `sub`); each view has its own file (`Overview`, `Orders`, `OrderDetail`, `RuleWatchPage`, `DataRoom`, `PlaybookPage`, `DemoDialogs`), shared bits are in `ui.tsx` and `OrderTable.tsx`. Larger lazy-loaded pages (`Analysis`, `OrderStatus`, `Reports`, `Regulations`, `KnowledgeBase`, `TradeMap`, `CompanySettings`) stay in `frontend/src/`. A new workspace page is a file plus an entry in `routes` and in `nav` or `ruleTabs`. One sidebar item, "Rules & news" (`ruleTabs` in `Workspace.tsx`), groups News watch, Rule watch, Regulations, the Playbook and the Knowledge base under a tab bar; each keeps its own route (`news`, `rules`, `regulations/...`, `playbook`, `knowledge`), so deep links are unchanged. Signed in, Rule watch (`RuleWatch.tsx`) starts with "Coming up": checklist lines that take effect or change within `RULE_WATCH_DAYS` (default 90; the page shows the window the API returns) in the markets of open orders (`GET /trade-map/changes`, the same list the company report's changes section uses).
- `frontend/src/Landing.tsx` is the public landing (`#/`); `frontend/src/TradeGlobe.tsx` is a Three.js globe that is lazy-loaded into its own chunk (Vite's 500 kB chunk warning for it is expected). The Firebase SDK and PapaParse are also loaded on demand, keeping the main chunk under 500 kB.
- Trade map (`#/workspace/map`, deep links `map/order/<id>`, `map/market/<code>`, `map/supplier/<name>`): `frontend/src/TradeMap.tsx` (the page and its state) is lazy-loaded; its parts are in `frontend/src/trade-map/`: `model.ts` (types, views, projections, pure helpers), `MapCanvas.tsx` (the 2D map and label placement), `panels.tsx` and `PlacePanels.tsx` (side panels), `forms.tsx` (supplier and site forms), `FloodPanel.tsx`, `ScenarioPanel.tsx`. Its world view uses `TradeMapGlobe.tsx` (Three.js, OrbitControls, world-atlas texture, elevated arcs and animated route particles); regional views and the optional 2D world view use d3-geo (110m for the world, 50m on demand for regional views). The globe has pause/zoom/reset controls, reduced-motion support and a WebGL fallback. Editors add and edit suppliers and sites in the side panel; while a form is open the map is 2D and a click sets the location (`projection.invert`) and suggests the country. Routes use a site marked `isRouteOrigin` when one exists; otherwise the world view draws an approximate start from the company profile's named origin (Vietnam, Singapore, Indonesia or Thailand) and says that point is not a recorded site. Connections are illustrative, not vessel tracking. The compare ("What if") panel (`trade-map/ScenarioPanel.tsx`) can save a what-if with a note (`ScenarioNotes.tsx`, `/trade-map/scenarios`, `services/scenarios.py`): a proposal on record that changes nothing on the order, with the comparison stored as it stood; an editor can start the note from a Gemini reading of the comparison (`/suggest`, points checked against the comparison's lines, not saved). All map data comes from the backend (`GET /api/v1/trade-map`, `GET /api/v1/trade-map/compare`), so the map only works in a connected session; the browser-only demo shows a sign-in prompt instead. Only map geometry (projections, camera presets, label placement) lives in the frontend.
- `frontend/src/Account.tsx` + `frontend/src/account-store.ts` + `frontend/src/auth.ts`: sign-up, sign-in, email verification and password reset use Firebase Auth (SDK loaded on first use, and preloaded on the sign-in pages so the "Continue with Google" popup isn't blocked; Google is hidden in dev auth mode and needs the OAuth client in `infra/terraform/README.md`). With `VITE_AUTH_MODE=dev` the Vite dev server accepts any password and sends `dev:<email>` tokens. "Explore the demo" opens the browser-only sample workspace with no account. After sign-in (or the demo), `intendedRoute()` returns to the workspace page that sent the visitor to `#/login`.
- Two kinds of session (`em-session` in sessionStorage): `demo` keeps orders, playbook rules, profile and demo state in browser storage (localStorage: `em-orders`, `em-rules`, `em-sent`, `em-demo-profile`); `api` reads and writes them through the backend (`frontend/src/api.ts`). In the workspace, `frontend/src/workspace/store.ts` (`useWorkspace()`) is the one place that tells them apart: orders, rules and CSV imports go through its demo or API source, and views branch on `live` only for wording and for features the demo lacks. `em-profile` is only a cache of `GET /me` (and of the email awaiting verification), removed on sign-out. `getProfile`/`putProfile` pick the key by session, so an account's details never show in the demo. Other sessionStorage keys: `em-next` (page to return to), `em-chat` and `em-chat-session` (chat history and audit session, cleared on sign-out and sign-in). The first-visit workspace tour (`frontend/src/Tour.tsx`: a spotlight on each sidebar item via `data-tour` attributes, skippable, replayed from the ? in the top bar) shows once per browser (localStorage `em-tour-done`); `playwright.config.ts` sets that key so the tour doesn't cover other tests, and `tests/tour.spec.ts` clears it. Seed data is in `frontend/src/data.ts`, with the demo's one sample rule change (`sampleObligation`, `sampleSuppliers`, `sampleCheck`, `sampleCosts`): every demo order, imported ones included, is checked against it, and the demo's counts, costs and dates are worked out from the orders and today's date (seed ship dates count from today). The demo's CSV checks (`frontend/src/order-csv.ts`) mirror the backend's. The AI service reads a signed-in company's orders and playbook rules (`query_orders`, `get_playbook`) with the user's token; a demo chat request carries the demo's orders (each with its sample check) and switched-on rules (`demoWorkspace()` in `frontend/ai/chat/agent-client.ts`).
- The "five-agent review" / rule-change demo in the workspace is simulated client-side for the browser demo only; it is unrelated to the real agent in `ai/server`.
- Phase 2/3 screens for a signed-in company (each lazy-loaded): `frontend/src/Analysis.tsx` (Orders page "Analyse orders" run panel; on an order's page, first under its facts, its latest analysis report from `latestReportId` with its next moves as buttons (`NextMoves.tsx`, worked out from the report's order, market, checks and suggested action: the order's own form opened at the HS code, destination, ship date or supplier field via `OrderFacts`' `editRequest`, or the trade map's supplier form in place, `SupplierFix.tsx`, with the documents the order's checklist asks for first), owner review, feedback, HS code suggestions for an order without a code, and supplier messages drafted → approved → sent), `CompanySettings.tsx` (Account: cost settings, owner-only activity log: the latest 10 events, the whole log as a CSV from `GET /audit-events/export`), `Playbook.tsx` (WHEN/THEN rule builder from `GET /playbook/fields`), requirement drafting and review on a regulation's page (`Regulations.tsx`), certificate upload in the trade map's supplier panel. The landing contact form posts to `POST /api/v1/contact` without a token.

### AI code (`ai/`)

- `frontend/ai/chat/` and `frontend/ai/news/` are frontend TSX modules imported by `frontend/src/main.tsx` and `frontend/src/workspace/` (and included in `frontend/tsconfig.json`), not a separate app. `frontend/ai/chat/agent-client.ts` defines the shared API types (`Audit`, `AuditStep`, `Citation`) and the base URL (`VITE_CHAT_API_URL`, default `/api`).
- `ai/server/index.js`: raw `http` server with manual route dispatch (`/api/chat` streams NDJSON; also `/api/audits`, `/api/inventory`, `/api/impacts`, `/api/scan`, `/api/sources`). With `AGENTS_AT` set (`runtime`: the Agent Runtime instance `AGENT_RUNTIME`, via Agent Platform's `streamQuery` / `query`; or a URL of a local `runtime.js`), `/api/chat` and `/api/memories` relay to the agents (`agents/remote.js`) instead of running them in-process; the user's backend token travels per call and is never stored. Config via env: `PORT`, `PROJECT_ID` (read before `GOOGLE_CLOUD_PROJECT`, which Agent Runtime sets to the project number), `AGENTS_AT`, `AGENT_RUNTIME`, `RAG_BUCKET` / `RAG_LOCATION` / `RAG_EMBED_MODEL` (RAG Engine, default `<project>-kb`, asia-southeast1, text-multilingual-embedding-002), `GEMINI_LOCATION` (default global), `GEMINI_MODEL_SIMPLE` / `GEMINI_MODEL_COMPLEX` (the assistant's two tiers, default gemini-3.5-flash-lite / gemini-4-argon, see `models.js`; `GEMINI_THINKING_SIMPLE` / `GEMINI_THINKING_COMPLEX` set their thinking levels, default LOW / MEDIUM), `GEMINI_MODEL` (news scan and eval judge, default gemini-3.5-flash; `GEMINI_THINKING_SCAN` its thinking level, default MEDIUM; Gemini 2.x models are sent no level, they refuse one), `SCAN_MAX_AGE_DAYS` (the scan's age rule, default 365, 0 = none), `ALLOWED_ORIGINS`, `SCHEDULER_SA`, `SCAN_AUDIENCE`, `GOOGLE_CLOUD_PROJECT`, `BACKEND_URL` (company backend origin, default `http://127.0.0.1:8000`), `CHAT_LIMIT_PER_CLIENT` / `CHAT_LIMIT_PER_INSTANCE` (chats per hour, default 40 / 200, counted in memory; the client is the first `X-Forwarded-For` address), `SCAN_SCHEDULE` (how the assistant describes the scheduler job), `MODEL_ARMOR_TEMPLATE` (full template name; unset turns Model Armor off). For a chat with a `Bearer` token (signed-in company workspace), `index.js` fetches `GET /api/v1/company/knowledge` with that token and passes the profile to the agent; failures fall back to the anonymous demo chat. News sources (`access.js`): built-in sources are shared by every workspace, and a company can switch one off only for itself (`companySources/{companyId}`); a custom source belongs to the company that added it, and only that company sees it and the articles and alerts it brought in (scan records carry `sourceIds` / `sourceCompanyIds`). The age rule (`access.js`): a scan skips articles older than `SCAN_MAX_AGE_DAYS`; a company can switch it off for itself (`PATCH /api/scan-rules`, `companySources/{companyId}.skipOld`, shown in `GET /api/sources` as `scanRules`), and then old articles are read from its sources and only it sees what they raise (records carry `ageDays`). Changing sources and starting a manual scan call `GET /api/v1/me` with the caller's token (cached for a minute) and accept only owners and editors (401 signed out, 403 other roles, 503 if the backend can't be reached). Reads take an optional token to apply the company's view. An audit made in a company workspace needs that company's token; the model's raw `thought` stays in Firestore and is never sent to clients. Request bodies over 100 KB get 413 (`limits.js`).
- `agent.js` (`runAgent`) runs one turn of the assistant, a Google ADK (`@google/adk`) multi-agent team built per turn in `agents/assistant.js`: a `RoutedAgent` (`exportmate_assistant`) whose router is `router.js` sends the question to `quick_answer` (simple tier, every read tool) or `analyst` (complex tier), which delegates to `stock_specialist`, `news_specialist`, `company_specialist` and `knowledge_specialist` (simple tier, each with its own tools) run as `SpecialistTool`s (an `AgentTool` in a session of its own). The auditor sends an answering agent's failing draft back once, to the analyst. Steps name their `agent`; specialists' reports are `delegate` steps; Memory Bank recalls are a `memory` step. Each answering agent has at most 6 model calls, a specialist 3 per request. Chats keep an Agent Platform session (`agents/platform.js`, Firestore `chat_sessions` maps a hash of user and browser session to it; a new one is seeded with the history the client sent), and signed-in company users have per-user Memory Bank memories (recalled before the turn into the prompt as data, learned from the question and answer after it; `GET`/`DELETE /api/memories`, Account › What the assistant remembers). Without `AGENT_RUNTIME`, sessions are in memory and nothing is remembered. The tools (`agents/tools.js` `REGISTRY`, each wrapped as an ADK tool that calls the gateway, with the calling agent's name): `search_knowledge`, `query_inventory`, `get_alerts`, `calculate`, `get_scan_status`, and scoped tools, offered and allowed only when the gateway's ctx has their `scope` (policy rules with `when` use the same names): `get_company_profile` (scope `company`, when a company profile was loaded; the system prompt then names that company and flags stock/alerts as demo data; cited as type `company`), `query_orders` (scope `orders`: the company's orders with their market checklists, read from `GET /api/v1/trade-map` with the user's own token, or the browser demo's orders sent with the question and checked by `orders.js` `demoMapOrders`; cited as type `order`, with each check's official text as type `regulation` deep-linking to its document version) and `get_playbook` (scope `playbook`: the switched-on rules from `GET /api/v1/playbook/rules`, or the demo's; cited as type `playbook`). `index.js` passes a `backend` reader for company chats and the client's `demo` data otherwise; a company chat never uses what the client sends. All tools are read-only. Every fact must carry a numbered citation. Each answer streams steps live and is stored as an audit record in the `audits` collection (with `policyVersion`, `requestId`, guard `flags`; `status` is `needs_review` when the final answer still fails the auditor). When changing tools or step shapes, keep `AuditStep` in `agent-client.ts` and the `Audit.tsx` renderer in sync. The harness around it (see `docs/AGENT_HARNESS.md`), all pure modules with tests in `test/`:
  - `policy.js`: the system-prompt rules; each names the failure it `prevents`. Add a rule (and a golden case) when a new failure is found; `POLICY_VERSION` is stored on audits.
  - `gateway.js`: every tool call is validated against its declared schema, scope-checked, budgeted per turn, timed out and retried only on transient errors; refusals return an `errorKind`. `withRetry` also wraps Gemini calls.
  - `guard.js`: third-party text (articles, alerts, custom feed names) addressed to the assistant is replaced with `[removed: …]` and flagged; `asData` fences text placed in prompts.
  - `review.js`: the auditor; citations resolve, figures and percentages appear in the user's messages or this turn's tool results, cited news carries its date, links are retrieved sources. A failing draft goes back once.
  - `router.js`: picks the model tier per question by rules (follow-up, several SKUs, arithmetic, trade rules, judgement, pasted text, injection, length → complex; else simple); `test/router.test.js` pins a tier for every golden case, so a new case must pick one. A simple-tier draft the auditor sends back is revised on the complex model. Models and thinking levels are in `models.js`.
  - `answer-cache.js`: the answer cache's key (normalised conversation, company, switched-off sources, policy, models, date, fingerprint of the tools' data) and which audits may be reused; `agent.js` reads and writes `answer_cache` in Firestore. Mark a tool `live: true` if it reads data outside that fingerprint (answers that call it aren't cached). Evals bypass the cache.
  - `rerank.js`: BM25 rerank of vector candidates (hybrid retrieval). `calc.js`: the calculator. `metrics.js`: audit aggregates for `ops.js` and the eval. `log.js`: JSON log lines on Cloud Run (one `chat.completed` per answer; never question text or tokens).
  - `eval/`: `golden.js` (cases with expectations computed from the live stock), `score.js` (answer + trajectory scoring), `run.js` (runner, optional LLM judge, regression check; results in the git-ignored `eval/results/`). `npm run eval:vertex` (`run.js --vertex`) also creates an Agent Platform evaluation run (`platform/evaluate.py`, a `uv` project using `agentplatform.Client().evals`): each case is exported as agent data (instruction, tool declarations, function calls and responses, answer; `runAgent` returns them as `trace` with `withEvidence`) and judged by managed metrics (final response quality, tool use quality, hallucination, safety). Runs go to the evaluation experiment "ExportMate assistant" on Agent Platform › Evaluation, in us-central1; local only, the Cloud Run image has no Python. `scan-golden.js` / `scan-score.js` / `scan-run.js` do the same for the news scan's relevance judgment (labeled articles, relevance and SKU precision/recall, and mention recall against each article's expected `mentions`, scored outside pass/fail; runs in `scan_eval_runs`).
- `rag.js`: search on Agent Platform RAG Engine. Each stock item, article, alert, source and help guide (`seed/guides.js`) is a text file in `RAG_BUCKET`, imported into the corpus for its type (`exportmate-kb-<type>`, created on first index; one folder and one import per type per indexing run, replaced files removed); Firestore `rag_files` keeps each record's metadata and RAG file. `search()` queries the wanted types' corpora in parallel (retrieveContexts takes one corpus), loads the records, drops what the caller may not see (`access.js`, before any agent reads it) and reranks with `rerank.js`. `removeDocs()` deletes records (a removed source).
- `agents/`: `assistant.js` (the agent tree), `tools.js` (tool registry, gateway tool, refs), `instructions.js` (prompts from `policy.js`; memories fenced with `guard.js` `asData`), `model.js` (shared Gemini client: per-call model and thinking level, retries, a per-tier timeout so a stalled call is retried), `platform.js` (Sessions, Memory Bank, user keys), `remote.js` (how the API reaches the agents).
- `runtime.js`: the agents behind Agent Runtime's runtime contract (`/api/reasoning_engine`: `query`, `list_memories`, `delete_memory`; `/api/stream_reasoning_engine`: `stream_query`, the same NDJSON events as `/api/chat`; the console playground's `{message}` runs as the demo; `channel: "eval"` returns evidence and trace for `eval/run.js --engine`). `main.js` starts it when `SERVE=runtime`, else `index.js`; `docker-entrypoint.sh` trusts the Agent Gateway's root CA (`AGENT_GATEWAY_CA`). `agents/telemetry.js` sends ADK's spans (no prompt or result text) to the Telemetry API, filed under the instance (its Traces tab); `GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY` (set by `platform/runtime.py`) turns it and the console's dashboards on.
- `platform/` (Python, `uv`): `runtime.py` creates or updates the Agent Runtime instance (Memory Bank topics and TTL, container image, `classMethods`, Agent Identity, min/max instances, optional egress gateway); `evaluate.py` creates Agent Platform evaluation runs. Govern is `infra/agent-platform/govern.sh`.
- `scan.js` + `feeds.js` + `candidates.js`: news scan — reads enabled RSS/Atom sources, keeps articles no scan analysed within the age rule (`candidates.js`, no fixed lookback, so articles a failed scan missed are retried), asks Gemini which SKUs each article affects and what it names (`mentions`: materials, HS codes, origin countries, markets; `mentions.js` keeps only well-formed values, for the backend's knowledge graph walk), writes `impacts` and indexes new articles/alerts. Article text is fenced in `<article>` tags; articles containing injected instructions or malicious links are withheld (`articlesWithheld`): `guard.js`'s patterns first, then Model Armor (`armor.js`, template from Terraform) when `MODEL_ARMOR_TEMPLATE` is set. An article Model Armor couldn't screen isn't recorded, so the next scan retries it (`articlesUnscreened`, `scan.armor_failed`); likewise articles in a Gemini batch that failed (`articlesFailed` + `error`, `scan.batch_failed`; a scan with none assessed is `failed`, and News watch's scan bar shows it). Triggered daily by Cloud Scheduler (OIDC-signed `POST /api/scan`, which bypasses the 10-minute cooldown); "Scan now" needs an owner or editor. A `locks/scan` document claimed in a Firestore transaction keeps two scans from running at once. After Gemini, `relevance.js` `decide()` keeps an article only if it names a SKU in stock, isn't a repeat of another article and doesn't name only goods the stock doesn't hold; `npm run eval:scan` scores this path. No code names an industry: the scan prompt, `relevance.js`'s word lists, the assistant's demo brief and News watch's caption come from `seed/inventory.js` `STOCK_PROFILE` (whose stock it is, the words news uses for its goods, goods that share its rules), and `query_inventory`'s category and market enums from the stock itself (`withStockLists`). Items carry `material`, `materialOrigin` and `originTraced`. A signed-in company's News watch and assistant use its own goods instead of the sample stock: `goods.js` (pure) builds them from `GET /company/knowledge` and `GET /trade-map`'s orders, `goods-store.js` keeps them in Firestore `companyGoods/{companyId}` and rebuilds them with a member's token when over 15 minutes old (`/api/inventory`, chats), and the scan assesses each company's goods too (`scanCompanies`, with a two-week read-back on its first scan). Company alerts carry `companyId` and an id of their own (`<articleId>~<companyId>`); `access.js` `goodsVisible` shows them only to that company and the sample stock's alerts and items only to the demo, and `presentScan` gives each caller its own alert count. Feeds must be public HTTPS; `feeds.js` checks the address when the socket connects (so DNS rebinding can't reach private or metadata addresses; NAT64/6to4 addresses are judged by the IPv4 inside) and stops reading past 3 MB.
- `db.js`: Firestore client and collection handles (`inventory`, `sources`, `articles`, `impacts`, `scans`, `answer_cache`). `rag_files`, `chat_sessions` and `audits` are accessed from `rag.js`, `agents/platform.js` and the agent/server code; the old `kb` vector collection is no longer read.

### Deployment wiring

- `frontend/vercel.json` rewrites `/api/*` to the Cloud Run URL; locally `frontend/vite.config.ts` proxies `/api` to `:8080`. Terraform reads that rewrite for the backend's `AI_SERVICE_URL`, so the backend reads the same AI service as the website.
- Browser → Vercel → Cloud Run `exportmate-ai` (`index.js`, its service account calls Agent Platform) → Agent Runtime instance (`runtime.js`, its own Agent Identity, egress through Agent Gateway). The same image serves both; `deploy.sh` updates both. Evaluation runs live in us-central1 (the service isn't offered in asia-southeast1); everything else is asia-southeast1 plus Gemini's global endpoint.
- `frontend/.vercelignore` excludes `ai/server` and `docs` from the Vercel upload; `ai/server/.gcloudignore` governs the Cloud Run source deploy.
